= LeanBun M5 Canonical Image Evidence
:toc: left
:sectnums:

== 状态

M5 第二阶段已实现只读 canonical image evidence。它重算 provider source、build-relevant config 和可选
artifact tree 的真实文件摘要，生成 ImageIdentity 与 image ID；当前不写 sealed attestation，不写项目
binding，也不执行 Lake。

[source,shell]
----
leanbun image evidence --artifacts=skip
leanbun image evidence --artifacts=full
----

`skip` 只完成 source/config/dependency identity；`full` 另读取全部 dependency `.lake/build` 文件字节。

== Canonical hash v1

所有记录按 owner 与 UTF-8 相对路径原始字节排序；摘要记录包含相对路径、类型、permission mode、size 与
真实文件 SHA-256。绝对安装路径、inode、device、mtime/ctime 不进入 identity，因此同字节的安全 clone
可复用同一身份。

Source policy `leanbun-source-tree-v1`：

* 排除 `.git` 和 `.lake` 整棵目录；
* 排除 `.DS_Store`；
* symlink 只记录 link target，不跟随；
* 使用 `O_NOFOLLOW`，打开前后复核 realpath、inode/device、size 和 mtime。

Config policy `leanbun-build-config-v1` 显式记录 provider toolchain、canonical registry SHA-256，以及每包的
`lean-toolchain`、`lake-manifest.json`、`lakefile.lean`、`lakefile.toml`；缺失文件本身也是规范记录。
location-specific override SHA-256 不进入 ImageIdentity；它仍由 sealed attestation 单独绑定，因此开发 COW
clone 与生产目录可共享身份，但不能混淆各自实际 override 证据。

Artifact policy `leanbun-artifact-tree-v1` 覆盖每个登记包 `.lake/build` 下的全部普通文件，而不只
`.olean`；只排除 `.DS_Store`、临时 lock、SQLite WAL/SHM。`.hash` 的真实字节会进入整树摘要，但其内容
不被当作其他文件的认证替代品。缺失 package build root 进入 hash，同时产生风险诊断。

在禁网、禁 Lake、只读 provider sandbox 中运行，未写 attestation：

|Source tree |`1a3ea443b0eedc360262af98fe2a162e37e9f6689da4f3b8dc17aceb6ac2a0fc`
|Source entries/files |11177 / 9776

|Artifact tree |`82c17f8c55668dd2a10040ed53eaebe742e8d06422a67f25c3968a71203abc12`
|Artifact entries/files |114937 / 112425
|Artifact bytes |6820362325
|Missing artifact roots |`Cli`

|===

开发 COW provider 与生产 provider 分别运行 source/config 模式后，规范化身份字段逐字节相同，SHA-256
都是 `f8355882cd9c1d2ed7b4d475fb220d8468fb0a0137121014b007f38bd1d5baef`。这验证了绝对
override 路径不污染 ImageIdentity；两次运行仍各自检查实际 override 文件和包路径。

Image ID 不含 artifact tree：相同源码/配置可在构件重建后保持镜像身份；sealed attestation 必须另绑定该
次实际 artifact tree hash。合成测试已验证修改 `.olean` 会改变 artifact tree，但不会改变 image ID。
