= LeanBun M5 Atomic Attestation Seal
:toc: left
:sectnums:

== 状态

M5 第三阶段已实现中央 image attestation 的显式原子封存。命令在封存前重新计算完整
source/config/dependency/artifact evidence，并再次检查 provider；它只写 `LEANBUN_STATE_ROOT`，不写项目、
不写 provider，也不执行 Lake。

[source,shell]
----
leanbun image seal [--allow-missing-artifact=<package>]...
----

缺失 artifact root 必须与命令给出的 allowlist 精确相等。多报、少报和拼写错误都会返回
`ATTESTATION_POLICY_REJECTED`；获准的缺失根写入 attestation，不能只存在于终端参数或日志中。

== Seal transaction v1

. 重新计算 canonical image evidence，要求 provider clean/matched；
. 读取完构件字节后再次检查 registry、override、Git revision 和工作树状态；
. canonicalize state root，拒绝 symlink `attestations/`；
. 以 `O_EXCL | O_NOFOLLOW` 创建每个 Image ID 的协作锁；
. 在目标同目录以 `O_EXCL | O_NOFOLLOW` 创建随机临时文件；
. 写入 canonical JSON，执行文件 `fsync`，设置 `0444`，再次 `fsync`；
. 在持锁状态下原子 rename 为 `<image-id>.json`，随后对目录 `fsync`；
. 用稳定、受 containment 约束的 reader 立即回读，核对 schema、SHA-256、完整 JSON 和 mode；
. 删除协作锁并再次同步目录。

目标已存在时不会覆盖。证据字段完全相同则返回 `already-sealed` 并保留原始 `sealedAt`；相同 Image ID
但 artifact/provider/policy 不同则返回 `ATTESTATION_SEAL_CONFLICT`。崩溃后遗留的锁不会被自动删除，
必须先人工审计目标与临时文件，避免把并发事务误判为 stale。

在禁网、禁 Lake、production provider 只读的 sandbox 中运行；唯一写入位于开发 state root：

封存文件为 `.leanbun-dev/state/attestations/<image-id>.json`。它绑定 production override SHA，而不是开发
COW override；production registry、override、Bun 和九包工作树在封存后另行复核无变化。

真实项目 `grsc-zeta-modern-arithmetic/lean` 在该 seal 已存在的情况下再次执行 preflight，仍因 binding
missing 以 exit `3` 拒绝，诊断保持为 `BINDING_MISSING`、`BUILD_NOT_AUTHORIZED`、
`LAKE_BUILD_NOT_ATTEMPTED`。项目封存前后 tree hash 都是
`87c996c61bf12093aafce7edb4bfb92a466966e2842fdce1da0ca5df716d79fd`，规范化快照逐字节相同。

== 已验证故障边界

测试覆盖同证据幂等、不一致证据不覆盖、symlink store 拒绝、临时文件与锁清理、缺失根默认拒绝、精确
allowlist 封存，以及 `.olean` 改变后同 Image ID 的 seal 冲突。封存成功不等于 build 授权：preflight
仍会独立重算 tree，且没有项目 binding 时固定拒绝。
