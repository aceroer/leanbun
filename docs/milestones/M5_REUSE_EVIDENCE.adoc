= LeanBun M5 Repeated-Build Reuse Evidence
:toc: left
:sectnums:

== 状态

M5 第十三阶段已建立 repeated-build reuse 的证据基础，但尚未启用跳过 Lake。新的 successful execution
record 同时绑定内容寻址的项目输入树与项目输出树；旧记录和缺少该对象的记录一律不具备复用资格。

== 输入域

`leanbun-project-input-tree-v1` 从 canonical project root 计算真实文件 SHA-256，并记录目录/文件 mode、
entry count、file count 与 byte count。它排除纯生成状态：

* `.git`；
* 整个 `.lake`，包括已有 build/config；
* `.leanbun/tmp`；
* `.DS_Store`。

项目源码、`lakefile`、`lean-toolchain`、`lake-manifest.json` 与 `.leanbun/binding.json` 都保留在输入域。
因此已有输出或临时日志变化不会误伤复用 identity，而源码、manifest、toolchain 或 binding 任一字节变化都会
产生新 identity。

== 输出域

`leanbun-project-output-tree-v1` 单独哈希完整 `.lake/build`。输出根必须真实存在；缺失时产生
`PROJECT_OUTPUT_MISSING`，不能把成功执行升级为可复用记录。输入必须在 Lake 前后保持同一内容摘要，否则产生
`PROJECT_INPUT_DRIFTED`。只有其他全部受控构建条件也通过时，terminal record 才带 `reuseEvidence`，并产生
`REUSE_EVIDENCE_RECORDED`。

这一阶段没有建立 latest-record index，没有选择候选记录，也没有返回 reused 状态；因此不会因为“找到旧记录”
而绕过 lock、attestation re-verification、dependency artifact 验证或 Lake。

== 测试

树哈希测试确认修改 `.lake/build` 和 `.leanbun/tmp` 不改变输入 identity，而修改 binding 会使其变化。
execution store 测试确认两种 schema、摘要和计数经过 atomic terminal publication 后仍能严格回读。
controlled-build 合取测试要求输入稳定且输出根存在。
