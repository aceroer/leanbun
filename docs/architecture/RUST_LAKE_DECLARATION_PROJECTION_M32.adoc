= LeanBun Rust Lake Declaration and Projection Bridge M32
:toc: left
:sectnums:

== Outcome

M32 is complete. The new `leanbun-lake-bridge` crate connects the M31 Bun authority model to Lake without giving Lake dependency-selection authority:

* `LakeRootDeclarationV1` normalizes bounded root declarations from `lakefile.toml` and `lakefile.lean`;
* `LakeManifestProjectionV1` emits the complete locked manifest view;
* `LakeRuntimePackagesProjectionV1` emits a path-only runtime packages file from the complete `PackagePathDecisionSetV1`;
* `LakeWorkspacePathObservationV1` compares every observed Lake package path against the unique Bun decision;
* typed errors reject duplicate/missing/extra packages, source kind/value drift, non-Bun runtime files and workspace path drift.

M32 does not select versions, fetch dependencies, publish store objects, write a real project or execute a target build.

== Root declaration probe

`lean/probes/M32RootDeclarations.lean` calls only exact-toolchain `Lake.loadWorkspaceRoot`. For Lean configuration files the native probe imports the complete Lake DSL and loads the co-located `libLake_shared` plugin so compiled command elaborators and evaluated configuration code come from the same locked Lake installation.

The Rust adapter:

. accepts a source project only below the fixture root;
. requires a new staging directory below `.leanbun-dev`;
. copies only the selected Lake config, `lean-toolchain` and probe source into staging;
. compiles and links the probe with the exact Lean 4.32 toolchain;
. runs compilation, linking and probing through the network-denying Seatbelt profile with a cleared environment;
. bounds stdout/stderr, strictly decodes schema v1 JSON and rechecks the source config/toolchain hashes;
. rejects any probe that creates `lake-manifest.json` or `.lake/packages`.

Both TOML fixtures and a real `lakefile.lean` DSL fixture pass this route. It does not call `Lake.loadWorkspace`, `lake update`, dependency materialization or target construction.

== Projection authority

Both projections are pure canonical JSON encoders. Package metadata must cover the complete locked closure exactly once and follows M31 canonical package ordering.

The manifest projection carries locked Git revision/subdirectory or locked path source data. Root declarations must agree with the lock on source kind and source value. Missing metadata does not fall back to an existing manifest.

The runtime projection has a narrower contract: every entry is `type = path`, its directory is the Bun-selected absolute final path, and construction requires a complete M31 decision set. A managed invocation is valid only with exactly one packages file and that file must be Bun-generated; duplicate `--packages`, absent projection and external runtime overrides fail closed.

`LakeWorkspacePathObservationV1` sorts the actual closure by package key, rejects duplicate/missing/extra observations and requires field-for-field equality with the decision set before producing an observation digest.

== Exact Lake and Mathlib acceptance

`lean/probes/M32ParseEntries.lean` is the exact Lake oracle. It calls `Lake.Manifest.parseEntries` on both Rust projections and reports the normalized entry fields. The tests establish:

* both projections are accepted by Lake 4.32 and preserve package/source fields;
* Git subdirectories survive the manifest projection;
* runtime entries contain only Bun paths;
* three-layer authority conflicts, duplicate runtime files, source kind drift, missing-manifest fallback and actual-path drift are rejected;
* the tracked Mathlib manifest and development override fixture form a complete nine-package closure, and all nine runtime paths equal their Bun final-path decisions.
