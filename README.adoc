= LeanBun
:toc: left
:sectnums:

LeanBun is an external package lifecycle manager for Lean and Lake projects.
It applies Bun's package-management model and Rust-based transactional machinery
to dependency updates, locking, cache reuse, and failure recovery, while leaving
project configuration and target/build semantics to Lake and final compilation
authority to the Lean compiler and kernel.

The current version is `0.20.0-m48-dev`. It is a repository-tested,
*source-only development release*. It is not a general-purpose Lean package
registry client, and it does not authorize automatic takeover of arbitrary
external projects.

== Quickstart

=== Verify the public source

The shortest useful path verifies the public Rust workspace, historical crates,
release boundary, and documentation without touching an existing Lean project:

[source,shell]
----
git clone https://github.com/aceroer/leanbun.git
cd leanbun
./scripts/test-public.sh
----

This requires macOS and Rust `1.96.0`. It validates the source tree; it does not
install a `leanbun` executable or modify a production Lean/Elan/Lake provider.

To run the Bun/Lean integration suite as well, create the Git-ignored local
provider configuration and initialize the copy-on-write development environment:

[source,shell]
----
cp config/leanbun-local-provider.example.json \
  config/leanbun-local-provider.json
# Edit the seven local provider fields before continuing.

./scripts/dev setup
./scripts/dev check
----

All generated state remains below `.leanbun-dev/` or `.leanbun-dev-rust/`.
Tests use only registered fixtures and do not run `lake update` in an active project.

=== Build and try the M48 CLI

The CLI is integrated into a pinned Bun source tree, so a clone of this repository
alone does not contain a standalone `leanbun` Cargo binary. Follow
xref:docs/operator/LEANBUN_SOURCE_INSTALL_M48.adoc[M48 source installation] to
recreate the paired Bun fork and verify its tree identity. From that fork root:

[source,shell]
----
cargo build --locked --release -p leanbun

LEANBUN_REPOSITORY=/absolute/path/to/leanbun
LEANBUN_BIN="$PWD/target/release/leanbun"

"$LEANBUN_BIN" version
"$LEANBUN_BIN" doctor "$LEANBUN_REPOSITORY"
"$LEANBUN_BIN" inspect "$LEANBUN_REPOSITORY"
"$LEANBUN_BIN" fixture-regress "$LEANBUN_REPOSITORY"
----

`version`, `doctor`, and `inspect` are read-only. `fixture-regress` is the first
safe managed demonstration: it operates only on a registered repository fixture
and writes ignored regression evidence below `.leanbun-dev-rust/`.

== Brief usage guide

[cols="2,3,2",options="header"]
|===
|Intent |Command |State and authorization boundary

|Check binary compatibility
|`leanbun version`
|Read-only; reports versioned lock/binding/generation reader support.

|Check a LeanBun source tree
|`leanbun doctor <leanbun-repository>`
|Read-only; verifies the source-lock hash and compiled Bun identity, reviewed Lake
source compatibility, platform, and registered fixture toolchain.

|Inspect without loading Lake configuration
|`leanbun inspect <leanbun-repository>`
|Filesystem-only inspection; does not execute `lakefile.lean`, `lake env`, or `lake query`.

|Export release evidence
|`leanbun export-evidence <leanbun-repository>`
|Read-only; reports binary/source provenance and signing state.

|Exercise the managed lifecycle
|`leanbun fixture-regress <leanbun-repository> [--fixture=<registered-name>]`
|Writes only isolated regression records and fixture copies. Registered names
include `lake-basic`, `lake-managed-dependency`, `mathlib-project`,
`negative-matrix`, and `concurrent-history`.

|Exercise network fetch
|`leanbun fixture-network-update <leanbun-repository>`
|Uses an in-process loopback server only; it does not enable public registry discovery.

|Evaluate adoption without mutation
|`leanbun adopt-dry-run <leanbun-repository> <registered-fixture> <target> --explicit-dry-run`
|Only registered fixtures are eligible; success remains `eligible-not-adopted`.

|Run managed mutation commands
|`leanbun adopt`, `update`, `build`, `recover`, or `rollback`
|Development/acceptance scope only. M48 does not authorize these commands for an
arbitrary external project, even when its Lake files appear compatible.
|===

For exact arguments, record locations, recovery rules, and fixture restrictions,
see the xref:docs/operator/LEANBUN_OPERATOR_MANUAL_V1.adoc[operator manual].

== Why LeanBun

Lake is very good at its intended job: interpreting a Lean project's package and
target declarations, constructing the build graph, and invoking Lean. The problem
appears when the same machinery is also expected to act as a workstation-wide,
transactional dependency manager for large and version-sensitive closures such as
mathlib. Those responsibilities require guarantees outside Lake's build-oriented
scope.

For the reviewed Lean `4.32.0` / Lake `5.0.0` surface, the concrete gaps are:

[cols="2,3,3",options="header"]
|===
|Lake behavior |Lifecycle gap |Operational consequence

|`lakefile.lean` is executable Lean configuration. Loading a workspace may create
`.lake` state, compile configuration, or materialize dependencies when a manifest
is absent.
|There is no generally safe, filesystem-only workspace query boundary.
|A command that appears observational, including environment or target discovery,
can execute project code or write project state before it is trusted.

|`lake update` resolves packages, rewrites the manifest, and changes materialized
Git checkouts as one project operation.
|Lake does not expose a candidate-generation, verify, atomic-activate, and rollback
transaction around the complete dependency closure.
|A failed or interrupted update can leave evidence spread across the manifest,
checkout directories, caches, and build state rather than one committed generation.

|Package paths can come from the manifest, workspace overrides, and runtime
`--packages` projections. Later provenance layers shadow earlier ones, and runtime
ordering can decide the winning path.
|There is no single portable authority that records every candidate provenance,
the conflict decision, and exactly one final canonical path per package.
|The same declared package can resolve to different bytes or directories depending
on local overrides and invocation order.

|A manifest can pin a Git revision after resolution, but the revision alone does
not attest the actual source tree, package configuration, extracted archive, or
compiled artifacts. A Reservoir version also needs an independently frozen
version-to-commit binding to detect a same-version rebound.
|Resolved identity and verified content identity are not one lock invariant.
|A matching version or commit string can be mistaken for a verified, reusable
package image.

|Mathlib's artifact cache restores build products and Lake may reuse existing
trace or `.hash` information. When usable artifacts are absent, an ordinary build
can correctly fall back to compiling dependency sources.
|Cache recovery is not byte-level attestation, and Lake does not distinguish
permission to compile project code from permission to rebuild a shared dependency.
|A routine project build can unexpectedly become a long mathlib rebuild, while a
cache hit still does not prove that every active artifact matches a sealed image.

|Lake coordinates a project's build, but independently invoked projects do not
share a content-addressed package publication transaction or a global immutable
image lock.
|Cross-project fetch deduplication, publication, crash recovery, retention, and
auditable rollback remain outside the project build graph.
|Concurrent projects can duplicate downloads or compilation and can contend over
shared mutable dependency state without one durable commit point.
|===

These are not reasons to replace Lake. They are reasons to put a package lifecycle
layer in front of it. LeanBun freezes each requested identity to an exact commit and
verified content identity, resolves the three provenance layers deterministically,
publishes packages into an immutable store, and activates a complete generation
only after verification. Normal builds are frozen and offline; update, recovery,
and rollback are explicit audited transactions. Lake then receives one complete
package-path projection and remains the authority for target/build semantics, while
Lean remains the authority for compilation and kernel checking.

The detailed source-derived boundary is documented in
xref:docs/architecture/BUN_LEAN_PACKAGE_TAKEOVER_M30.adoc[Bun-managed package takeover authority].

== Authority boundary

[cols="1,3",options="header"]
|===
|Component |Retained authority

|LeanBun / Bun
|Resolve and freeze dependency identities; manage the store, generations, locks,
transactions, recovery, and the complete package-path projection supplied to Lake.

|Lake
|Interpret `lakefile.lean`, project configuration, the target graph, and build
semantics; consume dependency paths already selected by LeanBun.

|Lean
|Perform compilation, elaboration, and kernel checking.
|===

By default, `inspect` reads only `lean-toolchain`, manifest, provider, Git, and
artifact metadata. It does not execute a project's `lakefile.lean`, `lake env`,
or `lake query`. See the
xref:docs/architecture/BUN_LEAN_PACKAGE_TAKEOVER_M30.adoc[current Lean/Lake authority boundary].

== Current status

Milestones M43--M48 establish the following repository closure:

* dependency layering is mechanically enforced for 10 default Rust crates and
  5 non-default historical/support crates;
* `leanbun-lock`, `leanbun-inventory-legacy`, and `leanbun-codec` are physically separated;
* Reservoir version-to-commit resolution uses an independent, versioned companion
  binding, and an ordinary update cannot accept a same-version rebound;
* immutable-store publication, active generations, concurrent history, failure
  recovery, and rollback are closed over registered repository fixtures;
* the Bun fork adapter is reproducible from a pinned upstream commit and seven
  repository patches; the production path has no TypeScript, Python, XPC,
  LaunchDaemon, or privileged ACL dependency;
* M48 retains `LeanBunLockV1` and `ReservoirBindingsV1` reader compatibility and
  includes upgrade/rollback replay from the protected M42 state.

Known limits remain explicit:

* unrestricted public Reservoir discovery is not enabled;
* silent adoption of ordinary external projects is never permitted, and general
  production authorization remains a later milestone;
* the release consists of source and a reproducible patch series, not an official
  signed binary or installer;
* macOS arm64 is the fully reviewed build platform.

See the xref:docs/roadmaps/LEANBUN_VERSION_ROADMAP_M43_M48.adoc[M43--M48 roadmap]
for exit gates. The xref:docs/README.adoc[documentation index] contains the full
historical evidence instead of duplicating it here.

== Architecture

[source,text]
----
explicit update / registered metadata
                 |
                 v
resolver -> lock + Reservoir binding -> immutable store
                                           |
                                           v
                              transactional generation
                                           |
                                           v
                            one complete Lake projection
                                           |
                                           v
                                     Lake -> Lean
----

The default Rust path is layered in dependency order:

[source,text]
----
core
  +-- codec --------+
  +-- evidence -----+--> lake-bridge --+
  +-- lock ---------+------------------+--> resolver -> store -> generation -> build -> managed
----

`inventory-legacy`, `plan`, `state`, `macos-acl-sys`, and `approval-macos`
remain in the Cargo workspace, but they are not `default-members` and are not
runtime prerequisites of the Bun-managed mainline.

== Build from source

=== Rust mainline

[source,shell]
----
cd rust
cargo test --locked
----

The workspace requires Rust `1.96.0`. The default command builds only the 10
mainline crates; repository scripts validate historical members separately.

=== Isolated Bun / Lean development environment

The development environment does not modify the production provider. Create a
Git-ignored local configuration from the example:

[source,shell]
----
cp config/leanbun-local-provider.example.json \
  config/leanbun-local-provider.json
# Fill in absolute paths for local Bun, Elan, package set, cache,
# registry, and overrides.

./scripts/dev setup
./scripts/dev check
./scripts/dev historical-check
----

`./scripts/dev check` runs Bun/Lean tests, documentation link checks, Rust fmt,
Clippy, and default Rust tests inside the repository-isolated environment. Bun
tests run in a dedicated process group under an external watchdog: timeout or
supervisor loss triggers `SIGTERM`, a bounded grace period, and then `SIGKILL`
for any surviving descendants. The default timeout is 600 seconds and can be
bounded explicitly with `LEANBUN_TEST_TIMEOUT_SECONDS`. See
xref:docs/development/DEVELOPMENT_ENVIRONMENT.adoc[Development environment] and
xref:TEST_PROJECT_BOUNDARY.adoc[Test project boundary] for fixture rules.

=== Rebuild the M48 Bun adapter

The pinned upstream commit, patch order, ignored vendor inputs, and tree identity
are recorded in xref:docs/operator/LEANBUN_SOURCE_INSTALL_M48.adoc[M48 source installation].
Do not treat a temporary local Bun fork or development binary as a repository release.

== Validation commands

[source,shell]
----
./scripts/check-docs
./scripts/check-crate-layering
./scripts/check-public-source
./scripts/check-test-supervisor
./scripts/dev check
./scripts/dev historical-check
----

`check-public-source` verifies the protected M42 evidence, absence of personal
absolute paths, local-provider ignore rules, Bun patch count, and crate layering.
Tests, fault injection, and acceptance must use registered repository fixtures;
external research projects are not substitutes for milestone acceptance.

== Repository layout

[cols="1,3",options="header"]
|===
|Path |Contents

|`rust/crates/`
|Mainline and historical Rust crates. Cargo `default-members` define the current mainline.

|`src/`, `test/`
|Early Bun/TypeScript inspection, evidence models, and regression tests. They are
not runtime dependencies of the M48 binary.

|`test/fixtures/`
|The only Lean/Lake fixtures permitted for development, fault injection, and milestone acceptance.

|`architecture/`
|Machine-readable crate graphs, API census data, protected digests, and layering baselines.

|`config/`
|Versioned contracts, sandbox profiles, release provenance, and the local-provider example.

|`distribution/`
|The redacted patch series used to rebuild the adapter from pinned Bun upstream.

|`docs/`
|Architecture, roadmaps, decisions, milestone evidence, operator documentation,
and versioned upstream references.

|Isolated development, Rust validation, documentation checks, public-source checks,
and architectural guards.

runtime or summary compatibility requirements: `TEST_PROJECT_BOUNDARY.adoc` and
the SHA-256-protected `RUST_CONCURRENT_HISTORY_REGRESSION_M42.adoc`.

== Release and security

The M48 release identity combines the LeanBun source commit/tree, pinned Bun
upstream, adapter patch tree, Cargo lock, toolchain, reader set, and regression
summary. A version string alone is not complete provenance.

Source distribution does not require a Developer ID or notarization. Any future
prebuilt macOS binary must define a separate signing, notarization, and installation
boundary. Every update or adoption remains explicit, auditable, and rollback-capable.
