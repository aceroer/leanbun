= LeanBun
:toc: left
:sectnums:

LeanBun is an external package lifecycle manager for Lean and Lake projects.
It applies Bun's package-management model and Rust-based transactional machinery
to dependency updates, locking, cache reuse, and failure recovery, while leaving
project configuration and target/build semantics to Lake and final compilation
authority to the Lean compiler and kernel.

The current version is `0.20.0-m48-dev`. It is a repository-tested,
*source-only development release*. It is not a general-purpose Lean package
registry client, and it does not authorize automatic takeover of arbitrary
external projects.

== Why LeanBun

Lake is the authority for describing and building Lean projects. Large,
version-sensitive dependency closures also need stricter lifecycle controls:

* a package/version identity must resolve to an exact commit and content identity;
* an ordinary build must not silently re-resolve, download, or rebuild locked dependencies;
* multiple projects should reuse a verified immutable store instead of rebuilding the same mathlib closure;
* update, publication, activation, recovery, and rollback must form one auditable transaction;
* Git, path, provider, and Reservoir inputs need deterministic precedence and one final path projection.

LeanBun therefore manages update authorization, resolved locks, source acquisition,
integrity, the immutable store, generations, transactions, concurrency, recovery,
and change reports. It does not reimplement Lake or replace the Lean compiler.

== Authority boundary

[cols="1,3",options="header"]
|===
|Component |Retained authority

|LeanBun / Bun
|Resolve and freeze dependency identities; manage the store, generations, locks,
transactions, recovery, and the complete package-path projection supplied to Lake.

|Lake
|Interpret `lakefile.lean`, project configuration, the target graph, and build
semantics; consume dependency paths already selected by LeanBun.

|Lean
|Perform compilation, elaboration, and kernel checking.
|===

By default, `inspect` reads only `lean-toolchain`, manifest, provider, Git, and
artifact metadata. It does not execute a project's `lakefile.lean`, `lake env`,
or `lake query`. See the
xref:docs/architecture/LEANBUN_LEAN_LAKE_API_BOUNDARY.adoc[Lean/Lake API boundary].

== Current status

Milestones M43--M48 establish the following repository closure:

* dependency layering is mechanically enforced for 10 default Rust crates and
  5 non-default historical/support crates;
* `leanbun-lock`, `leanbun-inventory-legacy`, and `leanbun-codec` are physically separated;
* Reservoir version-to-commit resolution uses an independent, versioned companion
  binding, and an ordinary update cannot accept a same-version rebound;
* immutable-store publication, active generations, concurrent history, failure
  recovery, and rollback are closed over registered repository fixtures;
* the Bun fork adapter is reproducible from a pinned upstream commit and seven
  repository patches; the production path has no TypeScript, Python, XPC,
  LaunchDaemon, or privileged ACL dependency;
* M48 retains `LeanBunLockV1` and `ReservoirBindingsV1` reader compatibility and
  includes upgrade/rollback replay from the protected M42 state.

Known limits remain explicit:

* unrestricted public Reservoir discovery is not enabled;
* silent adoption of ordinary external projects is never permitted, and general
  production authorization remains a later milestone;
* the release consists of source and a reproducible patch series, not an official
  signed binary or installer;
* macOS arm64 is the fully reviewed build platform.

See the xref:docs/roadmaps/LEANBUN_VERSION_ROADMAP_M43_M48.adoc[M43--M48 roadmap]
for exit gates. The xref:docs/README.adoc[documentation index] contains the full
historical evidence instead of duplicating it here.

== Architecture

[source,text]
----
explicit update / registered metadata
                 |
                 v
resolver -> lock + Reservoir binding -> immutable store
                                           |
                                           v
                              transactional generation
                                           |
                                           v
                            one complete Lake projection
                                           |
                                           v
                                     Lake -> Lean
----

The default Rust path is layered in dependency order:

[source,text]
----
core
  +-- codec --------+
  +-- evidence -----+--> lake-bridge --+
  +-- lock ---------+------------------+--> resolver -> store -> generation -> build -> managed
----

`inventory-legacy`, `plan`, `state`, `macos-acl-sys`, and `approval-macos`
remain in the Cargo workspace, but they are not `default-members` and are not
runtime prerequisites of the Bun-managed mainline.

== Build from source

=== Rust mainline

[source,shell]
----
cd rust
cargo test --locked
----

The workspace requires Rust `1.96.0`. The default command builds only the 10
mainline crates; repository scripts validate historical members separately.

=== Isolated Bun / Lean development environment

The development environment does not modify the production provider. Create a
Git-ignored local configuration from the example:

[source,shell]
----
cp config/leanbun-local-provider.example.json \
  config/leanbun-local-provider.json
# Fill in absolute paths for local Bun, Elan, package set, cache,
# registry, and overrides.

./scripts/dev setup
./scripts/dev check
./scripts/dev historical-check
----

`./scripts/dev check` runs Bun/Lean tests, documentation link checks, Rust fmt,
Clippy, and default Rust tests inside the repository-isolated environment. See
xref:docs/development/DEVELOPMENT_ENVIRONMENT.adoc[Development environment] and
xref:TEST_PROJECT_BOUNDARY.adoc[Test project boundary] for fixture rules.

=== Rebuild the M48 Bun adapter

The pinned upstream commit, patch order, ignored vendor inputs, and tree identity
are recorded in xref:docs/operator/LEANBUN_SOURCE_INSTALL_M48.adoc[M48 source installation].
Do not treat a temporary local Bun fork or development binary as a repository release.

== Validation commands

[source,shell]
----
./scripts/check-docs
./scripts/check-crate-layering
./scripts/check-public-source
./scripts/dev check
./scripts/dev historical-check
----

`check-public-source` verifies the protected M42 evidence, absence of personal
absolute paths, local-provider ignore rules, Bun patch count, and crate layering.
Tests, fault injection, and acceptance must use registered repository fixtures;
external research projects are not substitutes for milestone acceptance.

== Repository layout

[cols="1,3",options="header"]
|===
|Path |Contents

|`rust/crates/`
|Mainline and historical Rust crates. Cargo `default-members` define the current mainline.

|`src/`, `test/`
|Early Bun/TypeScript inspection, evidence models, and regression tests. They are
not runtime dependencies of the M48 binary.

|`test/fixtures/`
|The only Lean/Lake fixtures permitted for development, fault injection, and milestone acceptance.

|`architecture/`
|Machine-readable crate graphs, API census data, protected digests, and layering baselines.

|`config/`
|Versioned contracts, sandbox profiles, release provenance, and the local-provider example.

|`distribution/`
|The redacted patch series used to rebuild the adapter from pinned Bun upstream.

|`docs/`
|Architecture, roadmaps, decisions, milestone evidence, operator documentation,
and versioned upstream references.

|`scripts/`
|Isolated development, Rust validation, documentation checks, public-source checks,
and architectural guards.
|===

The repository root retains only entry points and two historical contracts with
runtime or summary compatibility requirements: `TEST_PROJECT_BOUNDARY.adoc` and
the SHA-256-protected `RUST_CONCURRENT_HISTORY_REGRESSION_M42.adoc`.

== Release and security

The M48 release identity combines the LeanBun source commit/tree, pinned Bun
upstream, adapter patch tree, Cargo lock, toolchain, reader set, and regression
summary. A version string alone is not complete provenance.

Source distribution does not require a Developer ID or notarization. Any future
prebuilt macOS binary must define a separate signing, notarization, and installation
boundary. Every update or adoption remains explicit, auditable, and rollback-capable.
